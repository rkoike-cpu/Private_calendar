# インフラ構成設計書(Personal Calendar)

Step 3で実装したバックエンド(Go)と、Step 6で実装したフロントエンド(Next.js)を、AWS上で稼働させるための構成を設計する。本書は構成の設計までを対象とし、構築は次のStepで行う。

## 概要

### 構成の特徴

**1台のEC2インスタンスの中で、フロントエンドとバックエンドを並べて動かす**構成にした。ALBとAuto Scalingで同じ構成のインスタンスを複数のアベイラビリティゾーン(AZ)に配置し、可用性とスケーリングを確保する。

この配置を選んだ最大の理由は、**ブラウザから見たときに単一のドメインで完結する**ことにある。Step 6では、ブラウザがNext.jsの`/api/*`を呼び、Next.jsがGoへ転送する形にしている。この関係をそのままEC2の中に持ち込めば、ローカルで動いている構成を変えずにクラウドへ載せられる。

```
ブラウザ → ALB → EC2 ─┬─ Next.js (:3000) ← ALBはここへ転送
                       └─ Go API (:8080) ← Next.jsが内部で転送
```

### 採用したサービス

| 層 | サービス | 用途 |
|---|---|---|
| DNS | Route 53 | 独自ドメインの名前解決 |
| 証明書 | ACM | ALBで使うHTTPS証明書 |
| 負荷分散 | ALB | HTTPS終端と、複数インスタンスへの振り分け |
| アプリ | EC2 + Auto Scaling | Next.jsとGoの実行 |
| データ | RDS for PostgreSQL(マルチAZ) | 永続化 |
| ネットワーク | VPC / サブネット / NAT Gateway | 通信経路の制御 |
| 権限 | IAM(インスタンスロール) | EC2からAWSサービスへのアクセス |
| 設定 | Systems Manager パラメータストア | 接続情報や鍵の保管 |
| 監視 | CloudWatch Logs | アプリケーションログの集約 |

### 通信の制御(セキュリティグループ)

各層は、直前の層からの通信だけを受け付ける。

| 対象 | 受け付ける通信 | 送信元 |
|---|---|---|
| ALB | 443 (HTTPS) | インターネット |
| EC2 | 3000 | ALBのセキュリティグループのみ |
| RDS | 5432 | EC2のセキュリティグループのみ |

Goの8080番はインスタンスの内部からのみ使うため、外部には一切開放しない。EC2とRDSはプライベートサブネットに置き、インターネットから直接到達できない配置にする。

## 選定理由

各サービスについて、どの選択肢と比較してなぜこれを選んだのかを記す。

### Route 53 — 独自ドメインの名前解決

| 比較した選択肢 | 採否 |
|---|---|
| ALBが自動で払い出すドメイン名をそのまま使う | 不採用 |
| 他社のDNSサービスで独自ドメインを管理する | 不採用 |
| **Route 53 で独自ドメインを管理する** | **採用** |

ALBの自動払い出し名は、ALBを作り直すと変わる。GoogleのOAuthはリダイレクト先URLを事前登録する方式のため、**アドレスが変わるたびにGoogle Cloud Console側の再設定が必要**になり、設定漏れがそのまま認証エラーにつながる。この理由から、自前の固定ドメインを持つ案を採った。

他社のDNSサービスでも固定ドメインは実現できるが、ALBへの紐付けとACMの証明書検証が同じ画面で完結する点を優先してRoute 53にした。

### ACM — HTTPS証明書

| 比較した選択肢 | 採否 |
|---|---|
| HTTPのまま運用する | **成立しない** |
| 他社の証明書を購入し、ALBへ手動で登録する | 不採用 |
| **ACMで発行し、ALBへ適用する** | **採用** |

HTTPのままという選択肢は、このアプリでは成立しない。GoogleのOAuthはリダイレクト先に`https://`を要求し、セッションCookieの`Secure`属性はHTTPSでなければ機能せず、プッシュ通知に必要なService WorkerもHTTPS上でしか登録できないためである。

残る2案のうちACMを選んだのは、**発行も更新も無料かつ自動**だからである。証明書の期限切れによる障害は運用でよく起きるが、手動更新の経路を持たないことでその可能性を断てる。

### ALB — HTTPS終端と振り分け

| 比較した選択肢 | 採否 |
|---|---|
| ロードバランサを置かず、EC2へ直接アクセスさせる | **要件を満たさない** |
| NLB(ネットワークロードバランサ) | 不採用 |
| **ALB(アプリケーションロードバランサ)** | **採用** |

ロードバランサを置かない案は、「一部のサーバに障害が起きても応答できる」という要件を満たせないため除外した。振り分け先を切り替える仕組みがなければ、落ちたインスタンスへアクセスが届き続ける。

NLBとの比較では、**ヘルスチェックの精度**が決め手になった。NLBはTCP接続の可否までしか見ないため、プロセスは生きているが内部の異常で500しか返せない状態を正常と判断してしまう。ALBは「特定のパスへGETして200が返るか」を確認できるため、応答の正しさで切り離しを判断できる。

将来フロントエンドとバックエンドを別インスタンスに分ける場合に、パスによる振り分け(`/api/*`とそれ以外)へ移行できる点も、NLBにはない利点として考慮した。

なおHTTPS終端をALBに集約することで、証明書を各インスタンスへ配る必要がなくなる。インスタンスが自動で増減する構成では、この集約が効く。

### EC2 + Auto Scaling — アプリケーションの実行

| 比較した選択肢 | 採否 |
|---|---|
| EC2を1台だけ固定で動かす | **要件を満たさない** |
| ECS / EKS(コンテナ基盤)で動かす | 不採用 |
| **EC2 + Auto Scaling(最小2台 / 最大4台)** | **採用** |

1台構成は、そのインスタンスが落ちた瞬間にサービスが止まるため、可用性の要件を満たせない。2台を別々のAZに置くことで、インスタンス単位の障害にもAZ単位の障害にも耐えられる。

コンテナ基盤との比較では、**得られる利点が現時点の規模に見合わない**と判断した。このアプリはGoのバイナリ1つとNode.jsのプロセス1つで動くため、コンテナ化で解決される問題(環境差異、依存関係の衝突)がそもそも起きにくい。一方で、クラスタやタスク定義といった学ぶべき構成要素は確実に増える。まずEC2で構成を理解することを優先した。

台数の上限を4台としたのは、利用者が自分1人のため本来は負荷が増えないにもかかわらず、上限を設けないと誤った設定で台数が増え続けて費用が青天井になるためである。増減の判断には、段階的な設定を自分で組むより誤りが起きにくいターゲット追跡(CPU使用率の目標値)を使う。

### RDS for PostgreSQL(マルチAZ) — データの永続化

| 比較した選択肢 | 採否 |
|---|---|
| EC2にPostgreSQLを自前で立てる | 不採用 |
| RDSのシングルAZ構成 | 不採用 |
| **RDSのマルチAZ構成** | **採用** |

自前で立てる案は、バックアップの取得・パッチの適用・障害時の切り替えをすべて自分で作り込む必要がある。これらは本来のアプリ開発とは別の作業であり、マネージドサービスに任せたほうが確実性が高い。

シングルAZとの比較では、**アプリ側だけ冗長にしてもDBが単一障害点として残る**点が決め手になった。EC2を2台にしてもDBが1台構成なら、そこが落ちた時点でサービスは止まる。マルチAZでは別のAZに待機系が自動で用意され、障害時には自動で切り替わる。

なお現在のアプリはPostgreSQLを使っているため、接続先を変えるだけで移行できる。

### VPC・サブネット・NAT Gateway — 通信経路の制御

| 比較した選択肢 | 採否 |
|---|---|
| EC2・RDSをパブリックサブネットに置く | 不採用 |
| **3層に分け、EC2・RDSはプライベートサブネットに置く** | **採用** |
| NAT Gatewayを1つだけ置く | 不採用 |
| **NAT GatewayをAZごとに置く** | **採用** |

パブリックサブネットに置く案は、設定が単純になる代わりに、EC2とRDSがインターネットから直接到達可能になる。サブネットを3層(パブリック / プライベート・アプリ / プライベート・DB)に分けることで、到達できる範囲を段階的に狭めた。

| 層 | 配置するもの | インターネットからの到達 |
|---|---|---|
| パブリック | ALB、NAT Gateway | 可能 |
| プライベート(アプリ) | EC2 | 不可 |
| プライベート(DB) | RDS | 不可 |

ただしこのアプリは外部APIを呼ぶ。Google Calendar APIでの予定の取得と更新、WeatherAPI.comでの天気取得、プッシュ通知の送信である。特にリマインダーは1分ごとにGoogleへ問い合わせるため、外向きの通信は常時発生する。内向きの接続を受け付けないまま外へ出るために、NAT Gatewayが必要になる。

NAT Gatewayの数については、1つにすれば費用は半分で済むが、そのAZが落ちると**もう片方のAZのインスタンスは画面こそ返せても予定を取得できない**状態になる。中途半端な応答を避ける観点から、AZごとに配置する案を採った。

### IAM(インスタンスロール) — 権限の管理

| 比較した選択肢 | 採否 |
|---|---|
| アクセスキーをインスタンス内のファイルに置く | 不採用 |
| **インスタンスロールを割り当てる** | **採用** |

アクセスキーをファイルに置くと、そのキーがインスタンスのイメージや設定ファイルに混入する経路が生まれる。Auto Scalingではインスタンスのイメージを複製して増やすため、この混入は全台に広がる。

ロールであれば、必要な権限が起動時に自動で付与され、認証情報の有効期限も自動で更新される。付与する権限は、パラメータストアの読み取り・CloudWatch Logsへの書き込み・Session Managerでの接続の3つに絞る。

### Systems Manager パラメータストア — 設定値の保管

| 比較した選択肢 | 採否 |
|---|---|
| AMIや設定ファイルに値を埋め込む | 不採用 |
| Secrets Manager | 不採用 |
| **パラメータストア(SecureString)** | **採用** |

Auto Scalingではインスタンスが自動で作られるため、起動したインスタンスが自力で設定値を取得できる必要がある。AMIに埋め込む案は、値を変更するたびにAMIを作り直すことになり、かつ値がイメージに残り続ける。

Secrets Managerとの比較では、こちらが持つ**鍵の自動ローテーション機能を今回は使わない**点が判断材料になった。その機能のぶん費用が発生するため、無料の範囲で使えるパラメータストアを選んだ。

保管する対象は、DBの接続情報・合言葉・WeatherAPIのキー・VAPIDの鍵・Google OAuthの認証情報である。

### CloudWatch Logs — ログの集約

| 比較した選択肢 | 採否 |
|---|---|
| インスタンス内のファイルにログを残す | 不採用 |
| **CloudWatch Logsへ送る** | **採用** |

インスタンスは自動で作られ、自動で破棄される。インスタンス内にログを置くと、**障害でインスタンスが入れ替わった際に、原因究明に必要なログごと消える**。最も知りたい場面で最も手に入らない、という状態になる。

外部に送っておくことで、インスタンスの生死と切り離してログを追える。Step 3でエラーをすべてログに残す方針にした判断が、ここで活きる。

## スケーリングによって顕在化する問題と、その対策

構成を考える過程で、**今のアプリをそのまま複数台で動かすと不具合が出る箇所**を1つ見つけた。

### リマインダーの二重送信

[`internal/reminder/reminder.go`](../internal/reminder/reminder.go) は、予定の10分前にプッシュ通知を送る処理を1分ごとに実行している。現在の流れは次の通りである。

```
1. 送信済みかDBに問い合わせる (HasReminderBeenSent)
2. 送信していなければ通知を送る (notifyAll)
3. 送信済みとしてDBに記録する  (MarkReminderSent)
```

1台で動かす限り問題はないが、**2台で動かすと両方が同時に手順1を通過し得る**。どちらも「まだ送っていない」と判断し、同じ予定について通知が2回届く。

原因は、確認と記録が別々の操作に分かれており、その間に他方が割り込めることにある。

### 対策

記録を先に行い、**記録できた側だけが通知を送る**順序に変える。

```
1. 送信済みとしてDBへ記録を試みる
2. 自分が記録できた場合だけ通知を送る
3. 他方が先に記録していた場合は何もしない
```

`sent_reminders`テーブルは`event_id`を主キーに持つため、同じIDの記録は1行しか作れない。この制約を使えば、「記録できたかどうか」で送信の権利を1台に絞れる。既存のSQLは`ON CONFLICT DO NOTHING`を使っているので、実際に行が追加されたかを見るだけで判定できる。

この変更は次のStepの構築時に行う。

## まとめ

### 構成を考える過程で検討したこと

- **フロントエンドの配置を3案で比較した**。(1) 今回採用したEC2に同居させる案、(2) Amplify Hostingに任せる案、(3) S3とCloudFrontで配信する案である。(3)は、Next.jsがサーバー側で動かしている処理(未ログイン時の転送、Google連携完了画面)を静的配信では実現できないため、アプリの作り変えが前提になり見送った。(2)は運用が最も楽だが、ドメインが分かれることでCORSとCookieの対応が増える。Step 6で「同一オリジンを保つことで認証の複雑さを避ける」判断をしているため、その一貫性を優先して(1)を選んだ
- **NAT Gatewayを2つ置くか1つにするか迷った**。AZごとに置けば片方のAZが落ちても外向き通信が維持できるが、費用は2倍になる。可用性の要件は「一部のサーバに障害が起きても応答できる」ことであり、外部API呼び出しの冗長化までは求められていない。ただしこのアプリは予定の取得に外部APIを使うため、片方のAZでNAT Gatewayが落ちると、そのAZのインスタンスは画面こそ返せても予定を取得できない状態になる。中途半端な応答を避ける観点から、AZごとに配置する案を採った
- **最小台数を1台にするか2台にするか迷った**。1台にすれば費用は半分になるが、障害が起きてから新しいインスタンスが起動するまでの数分間、応答できない時間が生まれる。「一部のサーバに障害が起きても継続的に応答できる」という要件を満たすには2台必要だと判断した

### 工夫したこと

- **Step 6で作った構成をそのまま持ち上げられる配置にした**。Next.jsがGoへ転送する関係をインスタンスの中に閉じ込めることで、アプリのコードを変えずにクラウドへ載せられる。「インフラに合わせてアプリを直す」のではなく、「アプリの構造を保てるインフラを選ぶ」という順序で考えた
- **アプリ側の前提が複数台構成に耐えるかを確認した**。セッションをDBに置いている点は問題なく動く一方、リマインダーの処理には二重送信の問題があることが分かった。構成図を描くだけでなく、その構成で既存のコードが正しく動くかまで見ることで、構築前に修正箇所を特定できた

### 学んだこと

- **台数を増やすと、今まで表に出なかった前提が問題になる**。リマインダーの処理は「自分だけが動いている」ことを暗黙の前提にしていた。1台で動かしている限り正しく、テストでも検出できない。スケーリングを設計の前提に置いて初めて見える種類の問題だと分かった
- **可用性は、一番弱い箇所で決まる**。アプリを2台にしても、DBが1台、NAT Gatewayが1つであれば、そこが落ちた時点でサービスは止まる。「どこを冗長にするか」ではなく「冗長でない箇所がどこに残るか」を数え上げる見方に切り替えると、判断がしやすくなった
- **費用と可用性は常に引き換えになる**。最小台数、NAT Gatewayの数、RDSのマルチAZは、いずれも可用性を上げる代わりに費用が増える。「要件が求めている水準はどこまでか」を基準に決めないと、過剰にも過少にもなると実感した
