# インフラ構成設計書(Personal Calendar)

Step 3で実装したバックエンド(Go)と、Step 6で実装したフロントエンド(Next.js)を、AWS上で稼働させるための構成を設計する。本書は構成の設計までを対象とし、構築は次のStepで行う。

## 概要

### 構成の特徴

**1台のEC2インスタンスの中で、フロントエンドとバックエンドを並べて動かす**構成にした。ALBとAuto Scalingで同じ構成のインスタンスを複数のアベイラビリティゾーン(AZ)に配置し、可用性とスケーリングを確保する。

この配置を選んだ最大の理由は、**ブラウザから見たときに単一のドメインで完結する**ことにある。Step 6では、ブラウザがNext.jsの`/api/*`を呼び、Next.jsがGoへ転送する形にしている。この関係をそのままEC2の中に持ち込めば、ローカルで動いている構成を変えずにクラウドへ載せられる。

```
ブラウザ → ALB → EC2 ─┬─ Next.js (:3000) ← ALBはここへ転送
                       └─ Go API (:8080) ← Next.jsが内部で転送
```

フロントエンドとバックエンドを別のドメインに分けると、CORSの設定とCookieの`SameSite=None`対応が新たに必要になる。同一オリジンを保つことで、認証まわりの複雑さを増やさずに済む。

### 採用したサービス

| 層 | サービス | 用途 |
|---|---|---|
| DNS | Route 53 | 独自ドメインの名前解決 |
| 証明書 | ACM | ALBで使うHTTPS証明書 |
| 負荷分散 | ALB | HTTPS終端と、複数インスタンスへの振り分け |
| アプリ | EC2 + Auto Scaling | Next.jsとGoの実行 |
| データ | RDS for PostgreSQL(マルチAZ) | 永続化 |
| ネットワーク | VPC / サブネット / NAT Gateway | 通信経路の制御 |
| 権限 | IAM(インスタンスロール) | EC2からAWSサービスへのアクセス |
| 設定 | Systems Manager パラメータストア | 接続情報や鍵の保管 |
| 監視 | CloudWatch Logs | アプリケーションログの集約 |

### 通信の制御(セキュリティグループ)

各層は、直前の層からの通信だけを受け付ける。

| 対象 | 受け付ける通信 | 送信元 |
|---|---|---|
| ALB | 443 (HTTPS) | インターネット |
| EC2 | 3000 | ALBのセキュリティグループのみ |
| RDS | 5432 | EC2のセキュリティグループのみ |

Goの8080番はインスタンスの内部からのみ使うため、外部には一切開放しない。EC2とRDSはプライベートサブネットに置き、インターネットから直接到達できない配置にする。

## 選定理由

### Route 53 — 独自ドメインの名前解決

ALBが自動で払い出すドメイン名は、再作成すると変わる。Googleの OAuth はリダイレクト先URLを事前登録する方式のため、**アドレスが変わるたびにGoogle Cloud Console側の再設定が必要になる**。固定のドメインを自分で持つことで、この手間と設定漏れを避ける。

他社のDNSサービスでも実現できるが、ALBやACMとの連携が設定画面上で完結する点を優先した。

### ACM — HTTPS証明書

HTTPSは、この構成では省略できない。理由が3つある。

- Googleの OAuth はリダイレクト先に`https://`を要求する
- セッションCookieに付ける`Secure`属性は、HTTPSでなければ機能しない
- プッシュ通知に必要なService Workerは、HTTPS上でしか登録できない

ACMを選んだのは、証明書の発行と更新が無料かつ自動で、ALBに直接適用できるためである。証明書の期限切れによる障害は運用でよく起きるが、自動更新に任せることでその経路を断てる。

### ALB — HTTPS終端と振り分け

非機能要件の「一部のサーバに障害が起きても応答できる」を実現する中心になる。

ALBは各インスタンスへ定期的にヘルスチェックを送り、応答しなくなったインスタンスを振り分け対象から自動で外す。これにより、1台が落ちてももう1台が応答を続けられる。

また、HTTPSの終端をALBに集約することで、証明書を各インスタンスへ配る必要がなくなる。インスタンスが増減する構成では、この集約が効く。

**この構成で成立する前提**: Step 6で、ログインのセッションをDBの`viewer_sessions`テーブルに保存する設計にしている。セッションがインスタンスの中にないため、リクエストがどのインスタンスに振り分けられても同じように認証が通る。同じ利用者を同じインスタンスへ固定する設定(スティッキーセッション)は不要である。

### EC2 + Auto Scaling — アプリケーションの実行

非機能要件の「需要の変動に合わせて台数を自動で増減できる」を満たす。

**最小2台**としたのは、可用性のためである。1台構成では、そのインスタンスが落ちた瞬間にサービスが止まる。2台を別々のAZに置くことで、AZ単位の障害にも耐えられる。

**最大4台**は、個人利用という規模に対する上限である。利用者が自分1人のため本来は負荷が増えないが、上限を設けないまま誤った設定で台数が増え続けると、費用が青天井になる。

増減の判断にはCPU使用率の目標値による制御(ターゲット追跡)を使う。段階的な設定を自分で組むより、目標値を1つ決めるだけで済み、設定の誤りが起きにくい。

**コンテナではなくEC2を選んだ理由**: このアプリはGoのバイナリ1つとNode.jsのプロセス1つで動く。コンテナやその管理基盤を導入すると、学ぶべき構成要素が増える一方で、得られる利点は現時点の規模では小さい。まずEC2で構成を理解することを優先した。

### RDS for PostgreSQL(マルチAZ) — データの永続化

現在のアプリはPostgreSQLを使っているため、接続先を変えるだけで移行できる。

**マルチAZ配置**を選んだのは、DBが可用性の弱点になりやすいためである。アプリ側を2台にしても、DBが1台構成ならそこが単一障害点になる。マルチAZでは別のAZに待機系が自動で用意され、障害時には自動で切り替わる。

**自前でEC2にPostgreSQLを立てない理由**: バックアップの取得、パッチの適用、障害時の切り替えをすべて自分で作り込む必要がある。これらは本来のアプリ開発とは別の作業で、マネージドサービスに任せたほうが確実性が高い。

### VPC・サブネット・NAT Gateway — 通信経路の制御

サブネットを3層に分け、インターネットから到達できる範囲を段階的に狭めている。

| 層 | 配置するもの | インターネットからの到達 |
|---|---|---|
| パブリック | ALB、NAT Gateway | 可能 |
| プライベート(アプリ) | EC2 | 不可 |
| プライベート(DB) | RDS | 不可 |

**NAT Gatewayが必要な理由**: このアプリは外部APIを呼ぶ。Google Calendar APIでの予定の取得と更新、WeatherAPI.comでの天気取得、プッシュ通知の送信である。特にリマインダーは1分ごとにGoogleへ問い合わせるため、外向きの通信は常時発生する。

EC2をプライベートサブネットに置いたまま外部へ出るには、NAT Gatewayが要る。内向きの接続は受け付けないまま、外向きの通信だけを通せる。

### IAM(インスタンスロール) — 権限の管理

EC2に対して、アクセスキーをファイルに置かず、ロールを割り当てる方式にする。キーの文字列をインスタンスの中に保存すると、そのインスタンスのイメージや設定ファイルに混入する経路が生まれる。ロールであれば、必要な権限が自動で付与され、期限も自動で更新される。

付与する権限は次の3つに絞る。

- パラメータストアから設定値を読む(読み取りのみ)
- CloudWatch Logsへログを書き込む
- Systems Manager のセッション機能で接続する

### Systems Manager パラメータストア — 設定値の保管

現在、DBの接続情報・合言葉・各種APIキー・Google OAuthの認証情報は、ローカルでは`.env`ファイル、Renderでは環境変数として管理している。

Auto Scalingではインスタンスが自動で作られるため、**起動したインスタンスが自力で設定値を取得できる必要がある**。パラメータストアに置き、起動時にインスタンスロールの権限で読み出す形にする。

Secrets Managerという選択肢もあるが、こちらは鍵の自動ローテーション機能を持つ代わりに費用が発生する。今回はその機能を使わないため、無料の範囲で使えるパラメータストアを選んだ。

### CloudWatch Logs — ログの集約

インスタンスは自動で作られ、自動で破棄される。インスタンスの中にログを置くと、**障害でインスタンスが入れ替わった際に、原因究明に必要なログごと消える**。外部に送っておくことで、インスタンスの生死と切り離してログを追える。

Step 3でエラーをすべてログに残す方針にした判断が、ここで活きる。

## スケーリングによって顕在化する問題と、その対策

構成を考える過程で、**今のアプリをそのまま複数台で動かすと不具合が出る箇所**を1つ見つけた。

### リマインダーの二重送信

[`internal/reminder/reminder.go`](../internal/reminder/reminder.go) は、予定の10分前にプッシュ通知を送る処理を1分ごとに実行している。現在の流れは次の通りである。

```
1. 送信済みかDBに問い合わせる (HasReminderBeenSent)
2. 送信していなければ通知を送る (notifyAll)
3. 送信済みとしてDBに記録する  (MarkReminderSent)
```

1台で動かす限り問題はないが、**2台で動かすと両方が同時に手順1を通過し得る**。どちらも「まだ送っていない」と判断し、同じ予定について通知が2回届く。

原因は、確認と記録が別々の操作に分かれており、その間に他方が割り込めることにある。

### 対策

記録を先に行い、**記録できた側だけが通知を送る**順序に変える。

```
1. 送信済みとしてDBへ記録を試みる
2. 自分が記録できた場合だけ通知を送る
3. 他方が先に記録していた場合は何もしない
```

`sent_reminders`テーブルは`event_id`を主キーに持つため、同じIDの記録は1行しか作れない。この制約を使えば、「記録できたかどうか」で送信の権利を1台に絞れる。既存のSQLは`ON CONFLICT DO NOTHING`を使っているので、実際に行が追加されたかを見るだけで判定できる。

この変更は次のStepの構築時に行う。

## まとめ

### 構成を考える過程で検討したこと

- **フロントエンドの配置を3案で比較した**。(1) 今回採用したEC2に同居させる案、(2) Amplify Hostingに任せる案、(3) S3とCloudFrontで配信する案である。(3)は、Next.jsがサーバー側で動かしている処理(未ログイン時の転送、Google連携完了画面)を静的配信では実現できないため、アプリの作り変えが前提になり見送った。(2)は運用が最も楽だが、ドメインが分かれることでCORSとCookieの対応が増える。Step 6で「同一オリジンを保つことで認証の複雑さを避ける」判断をしているため、その一貫性を優先して(1)を選んだ
- **NAT Gatewayを2つ置くか1つにするか迷った**。AZごとに置けば片方のAZが落ちても外向き通信が維持できるが、費用は2倍になる。可用性の要件は「一部のサーバに障害が起きても応答できる」ことであり、外部API呼び出しの冗長化までは求められていない。ただしこのアプリは予定の取得に外部APIを使うため、片方のAZでNAT Gatewayが落ちると、そのAZのインスタンスは画面こそ返せても予定を取得できない状態になる。中途半端な応答を避ける観点から、AZごとに配置する案を採った
- **最小台数を1台にするか2台にするか迷った**。1台にすれば費用は半分になるが、障害が起きてから新しいインスタンスが起動するまでの数分間、応答できない時間が生まれる。「一部のサーバに障害が起きても継続的に応答できる」という要件を満たすには2台必要だと判断した

### 工夫したこと

- **Step 6で作った構成をそのまま持ち上げられる配置にした**。Next.jsがGoへ転送する関係をインスタンスの中に閉じ込めることで、アプリのコードを変えずにクラウドへ載せられる。「インフラに合わせてアプリを直す」のではなく、「アプリの構造を保てるインフラを選ぶ」という順序で考えた
- **アプリ側の前提が複数台構成に耐えるかを確認した**。セッションをDBに置いている点は問題なく動く一方、リマインダーの処理には二重送信の問題があることが分かった。構成図を描くだけでなく、その構成で既存のコードが正しく動くかまで見ることで、構築前に修正箇所を特定できた

### 学んだこと

- **台数を増やすと、今まで表に出なかった前提が問題になる**。リマインダーの処理は「自分だけが動いている」ことを暗黙の前提にしていた。1台で動かしている限り正しく、テストでも検出できない。スケーリングを設計の前提に置いて初めて見える種類の問題だと分かった
- **可用性は、一番弱い箇所で決まる**。アプリを2台にしても、DBが1台、NAT Gatewayが1つであれば、そこが落ちた時点でサービスは止まる。「どこを冗長にするか」ではなく「冗長でない箇所がどこに残るか」を数え上げる見方に切り替えると、判断がしやすくなった
- **費用と可用性は常に引き換えになる**。最小台数、NAT Gatewayの数、RDSのマルチAZは、いずれも可用性を上げる代わりに費用が増える。「要件が求めている水準はどこまでか」を基準に決めないと、過剰にも過少にもなると実感した
