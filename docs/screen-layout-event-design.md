# 画面レイアウト・イベント設計書(Personal Calendar)

[画面設計書(画面一覧・画面遷移図)](./screen-design.md)で洗い出した4画面について、画面レイアウトと、各画面でいつAPIを呼ぶかというイベント設計を定義する。

対象画面は次の4つ。

| 画面ID | 画面名 |
|---|---|
| [SCR-001](#scr-001-ログイン画面) | ログイン画面 |
| [SCR-002](#scr-002-ダッシュボード画面) | ダッシュボード画面 |
| [SCR-003](#scr-003-予定追加編集ダイアログ) | 予定追加・編集ダイアログ |
| [SCR-004](#scr-004-google連携完了画面) | Google連携完了画面 |

---

## 画面レイアウト

### SCR-001 ログイン画面

#### 領域構成

```
┌────────────────────────────────┐
│                                │
│      Personal Calendar         │  ← タイトル
│                                │
│   ┌────────────────────────┐   │
│   │ 合言葉                 │   │  ← パスワード入力欄
│   └────────────────────────┘   │
│   ┌────────────────────────┐   │
│   │       ログイン         │   │  ← 送信ボタン
│   └────────────────────────┘   │
│                                │
└────────────────────────────────┘
      幅320pxで中央に配置
```

ヘッダー・フッター・サイドバーは持たない。入力欄とボタンだけを縦に並べた単一領域とする。認証前の画面であり、他へ遷移する導線を一切置かないことで、操作の迷いをなくす。

#### 各要素の目的

| 要素 | 種別 | 目的 |
|---|---|---|
| Personal Calendar | 見出し | どのアプリのログイン画面かを示す |
| 合言葉 | パスワード入力欄 | 合言葉を入力する。`type="password"`で入力値を伏せ字にし、`autofocus`で開いた直後から入力できる状態にする |
| ログイン | 送信ボタン | 入力した合言葉をサーバーへ送る |

#### 状態のバリエーション

| 状態 | 表示 |
|---|---|
| 初期表示 | 空の入力欄にカーソルが当たった状態 |
| 未入力で送信 | ブラウザ標準の必須入力エラー(`required`)が表示され、送信されない |
| 合言葉が誤り | サーバーが401と「パスワードが違います」を返し、ブラウザがその文面を表示する |
| 送信成功 | ダッシュボード(SCR-002)へ自動で遷移する |
| ローディング中 | 専用の表示は設けない。通常のフォーム送信のため、ブラウザのページ遷移表示に任せる |

#### レスポンシブ・アクセシビリティ

- 幅320pxの中央寄せとし、スマホでも横スクロールが発生しない
- 入力欄とボタンを`width: 100%`、`padding: 0.6rem`以上にして、指でタップしやすい大きさを確保する
- 合言葉の入力欄に`autofocus`を設定し、タップの手数を減らす

### SCR-002 ダッシュボード画面

#### 領域構成

```
┌──────────────────────────────────────────────┐
│ Personal Calendar  [🔔通知][+予定を追加][同期]│ ← ヘッダー
├──────────────────────────────────────────────┤
│ 最終同期: 12:30:45                           │ ← ステータス表示欄
├──────────────────────────────────────────────┤
│ 今日の天気                                   │
│ ┌──┬──┬──┬──┬──┬──┬──┐                      │ ← 天気ストリップ
│ │7時│8時│9時│10時│…│  │  │  (横スクロール)  │
│ │☀️ │⛅ │☁️ │🌧️ │  │  │  │                   │
│ │22℃│23℃│25℃│24℃│  │  │  │                   │
│ └──┴──┴──┴──┴──┴──┴──┘                      │
├──────────────────────────────────────────────┤
│ ToDo                                         │
│ [やることを入力    ][期限日 ][追加]          │ ← 入力フォーム
│ ☐ 資料を作る           2026-10-10      ✕     │ ← 一覧
│ ☑ メールを返す                         ✕     │
├──────────────────────────────────────────────┤
│                [日][週][月]                  │ ← 表示切替
│              [<] 10/6〜10/12 [>]             │ ← 日付ナビ
├──────────────────────────────────────────────┤
│      月  火  水  木  金  土  日              │
│  7時 ┊   ┊   ┊   ┊   ┊   ┊                  │
│  8時 ┊ ┌─────┐ ┊   ┊   ┊                    │ ← カレンダー本体
│  9時 ┊ │定例会│ ┊   ┊   ┊    (縦スクロール) │
│ 10時 ┊ └─────┘ ┊   ┊   ┊                    │
│  …                                          │
└──────────────────────────────────────────────┘
```

全体を縦1列に積む構成とする。上から「ヘッダー → 状態表示 → 天気 → ToDo → カレンダー」の順に並べ、スマホでもPCでも同じ並びとする。本文の最大幅は900pxで中央寄せとする。

#### 各要素の目的

| 領域 | 要素 | 目的 |
|---|---|---|
| ヘッダー | 🔔通知 | プッシュ通知の購読を切り替える。購読中は色を変えて状態が分かるようにする |
| ヘッダー | +予定を追加 | 予定追加ダイアログ(SCR-003)を新規モードで開く |
| ヘッダー | 同期 | Googleカレンダーから最新の予定を取得する |
| ステータス | ステータス表示欄 | 同期の進行状況、最終同期時刻、各操作の結果メッセージを表示する。1行の共用領域とし、画面内の操作結果をここに集約する |
| 天気 | 天気ストリップ | 今日1日の時間ごとの天気・気温・湿度を表示する。現在時刻の枠を強調し、今が何時かを一目で分かるようにする |
| ToDo | 入力フォーム | やることと期限日を入力して登録する。期限日は任意とする |
| ToDo | 一覧 | 未完了を上に、完了済みを下に並べる。チェックボックスで完了状態を切り替え、✕で削除する |
| カレンダー | 表示切替 | 日・週・月の表示を切り替える |
| カレンダー | 日付ナビ | 前後の日・週・月へ移動する |
| カレンダー | カレンダー本体 | 予定を時間軸のマス目に配置する。カテゴリ別に色分けし、現在時刻に赤い横線を引く |
| カレンダー | ポップオーバー | 予定にマウスを重ねたとき、件名・時刻・場所を拡大表示する(PCのみの補助表示) |

#### 状態のバリエーション

| 領域 | 状態 | 表示 |
|---|---|---|
| 全体 | 未ログイン | この画面は表示されず、ログイン画面(SCR-001)へ転送される |
| 天気 | ローディング中 | 「読み込み中...」 |
| 天気 | 取得失敗 | 「天気の取得に失敗しました」 |
| ToDo | 空状態 | 一覧に何も表示しない(入力フォームのみ) |
| ToDo | 完了済み項目 | 文字を薄くし、取り消し線を引く |
| カレンダー | 初期表示(同期前) | 枠線とマス目だけを表示する。予定は同期ボタンを押すまで表示しない |
| カレンダー | 同期中 | ステータス欄に「同期中...」 |
| カレンダー | 同期成功 | ステータス欄に「最終同期: 12:30:45」 |
| カレンダー | 同期失敗 | ステータス欄に「同期に失敗しました (status: 502)」 |
| カレンダー | Google未連携 | ステータス欄に「同期に失敗しました (status: 412)」 |
| 通知ボタン | 購読中 | ボタンに色を付けて区別する |
| 通知ボタン | 非対応ブラウザ | ボタン自体を隠す |
| 通知ボタン | 許可されなかった | ステータス欄に「通知が許可されませんでした」 |

#### レスポンシブ・アクセシビリティ

- 縦1列の構成とし、画面幅による並び替えを行わない。スマホを主たる利用環境とし、PCでは最大幅900pxで中央寄せとする
- 天気ストリップとカレンダーは横スクロール、カレンダー本体は高さ70vhまでで縦スクロールとし、狭い画面でも全体のレイアウトが崩れないようにする
- 天気は絵文字だけでなく、気温・湿度の数値を併記し、色や記号だけに依存しないようにする
- 予定の色分けは、カテゴリごとに明度差のある4色を使う
- ダイアログを開いたときに自動でフォーカスを当てず、スマホでキーボードが勝手に出ないようにする

### SCR-003 予定追加・編集ダイアログ

#### 領域構成

```
        ┌────────────────────────────┐
        │ 予定を追加 / 予定を編集     │ ← 見出し(モードで変わる)
        │                            │
        │ タイトル                   │
        │ [                        ] │
        │ 日付                       │
        │ [2026-10-08              ] │
        │ 開始時刻      終了時刻     │ ← 入力フォーム
        │ [10:00    ]   [11:00    ]  │
        │ 場所                       │
        │ [東京駅                  ] │
        │ 📍地図で見る               │ ← 場所入力時のみ表示
        │ カテゴリ                   │
        │ [仕事               ▼]     │
        │                            │
        │ ⚠ エラーメッセージ         │ ← エラー時のみ表示
        │                            │
        │ [削除]      [キャンセル][追加]│ ← 操作ボタン
        └────────────────────────────┘
           ダッシュボードの上に重ねて表示
```

ダッシュボード(SCR-002)の上に重ねるモーダルとして表示する。背景のカレンダーは暗転させ、操作できない状態にする。ページ遷移は行わず、閉じると元のカレンダーの表示状態(表示中の週・スクロール位置)がそのまま残るようにする。

#### 各要素の目的

| 要素 | 目的 |
|---|---|
| 見出し | 新規追加か編集かを示す。新規は「予定を追加」、編集は「予定を編集」 |
| タイトル | 予定の件名を入力する(必須) |
| 日付・開始時刻・終了時刻 | 予定の日時を入力する(すべて必須)。日付と時刻を分けて入力させ、スマホの日付・時刻ピッカーをそのまま使えるようにする |
| 場所 | 予定の場所を入力する(任意) |
| 📍地図で見る | 入力した場所をGoogleマップで開く。場所が未入力のときは隠す |
| カテゴリ | アプリ内だけの色分けを選ぶ(仕事・プライベート・重要・移動) |
| エラーメッセージ | 保存に失敗した理由を表示する。ダイアログを閉じずにその場で表示し、入力内容が失われないようにする |
| 削除 | 予定を削除する。新規追加時は隠す |
| キャンセル | 保存せずにダイアログを閉じる |
| 追加 / 更新 | 入力内容を保存する。新規は「追加」、編集は「更新」 |

#### 状態のバリエーション

| 状態 | 表示 |
|---|---|
| 新規モード | 入力欄は空。日付だけカレンダーで表示中の日付を初期値にする。削除ボタンは隠す。ボタンは「追加」 |
| 編集モード | クリックした予定の内容を各欄に入れた状態。削除ボタンを表示する。ボタンは「更新」 |
| 必須項目が未入力 | ブラウザ標準の必須入力エラーが出て送信されない |
| 終了時刻が開始時刻以前 | 「終了時刻は開始時刻より後にしてください。」を表示し、送信しない |
| 送信中 | 送信ボタンを押せない状態にし、二重送信を防ぐ。ステータス欄に「予定を追加中...」「予定を更新中...」 |
| 保存成功 | ダイアログを閉じ、カレンダーを描き直し、ステータス欄に結果を表示する |
| 保存失敗(権限エラー) | ダイアログは閉じず、エラー欄に「この予定はあなたが主催者ではないため変更できません(Googleカレンダーの仕様)」を表示する |
| 予定の更新は失敗、色の変更は成功 | ダイアログは閉じず、「(色の変更は反映しました)」を併記する |
| 削除の確認 | ブラウザ標準の確認ダイアログで「この予定を削除しますか?」と尋ねる |

#### レスポンシブ・アクセシビリティ

- HTML標準の`<dialog>`要素を使い、背景の暗転・Escキーで閉じる・フォーカスをダイアログ内に閉じ込める動作をブラウザの標準機能に任せる
- 入力欄はすべて`<label>`で項目名と結び付け、タップ領域を広くとる
- 日付・時刻の入力は`type="date"` / `type="time"`を使い、スマホでは標準のピッカーが開くようにする
- 開いたときに自動でフォーカスを当てず、スマホでキーボードが勝手にせり上がらないようにする

### SCR-004 Google連携完了画面

#### 領域構成

```
┌────────────────────────────────────────────┐
│ Googleカレンダーとの連携が完了しました     │ ← 完了メッセージ
│ (rkoike@netprotections.co.jp)              │    連携したアカウントを併記
│                                            │
│ ダッシュボードに戻る                       │ ← 戻るリンク
└────────────────────────────────────────────┘
```

メッセージと戻るリンクだけの最小構成とする。装飾(CSS)は持たせない。

#### 各要素の目的

| 要素 | 目的 |
|---|---|
| 完了メッセージ | 連携が成功したことと、どのGoogleアカウントと連携したかを伝える。意図しないアカウントで連携した場合に気づけるよう、メールアドレスを必ず表示する |
| ダッシュボードに戻るリンク | ダッシュボード(SCR-002)へ戻る |

#### 状態のバリエーション

| 状態 | 表示 |
|---|---|
| 連携成功 | 完了メッセージと戻るリンク |
| 許可リストにないアカウント | この画面は表示されず、403と「forbidden: this account is not allowed to authorize this app」を返す |
| 認可コードが無い | 400と「missing code」 |
| トークン交換に失敗 | 500と「token exchange failed」 |
| 未ログイン | この画面は表示されず、ログイン画面(SCR-001)へ転送される |

#### レスポンシブ・アクセシビリティ

CSSを持たないため、ブラウザ標準の表示に従う。文字と リンクだけの構成なので、画面幅によらず読める。連携直後に一度確認するだけの画面であり、装飾を加えないという判断自体を設計上の選択とする([設計判断](#4-scr-004-は装飾を持たせない)を参照)。

## イベント設計

### SCR-001 ログイン画面

| イベント | トリガー | 呼び出すAPI | 表示・処理内容 |
|---|---|---|---|
| 初期表示 | 画面を開く | 呼び出さない | 合言葉の入力欄にカーソルを当てる |
| ログイン送信 | 「ログイン」ボタン押下、または入力欄でEnter | `POST /login` | 成功: セッションCookieが発行され、ダッシュボード(SCR-002)へ自動で遷移する<br>失敗: 401と「パスワードが違います」が表示される |

### SCR-002 ダッシュボード画面

| イベント | トリガー | 呼び出すAPI | 表示・処理内容 |
|---|---|---|---|
| 初期表示(天気) | 画面を開く | `GET /api/weather/today` | 取得前は「読み込み中...」を表示し、取得後に時間ごとの天気ストリップを描画する。失敗時は「天気の取得に失敗しました」 |
| 初期表示(ToDo) | 画面を開く | `GET /api/tasks` | ToDo一覧を描画する。未完了を上、完了済みを下に並べる |
| 初期表示(通知ボタン) | 画面を開く | 呼び出さない | Service Workerを登録し、購読済みならボタンに色を付ける。非対応ブラウザではボタンを隠す |
| 初期表示(カレンダー) | 画面を開く | 呼び出さない | 枠線とマス目だけを描画する。予定は同期するまで表示しない |
| 現在時刻の更新 | 1分ごとの自動実行 | 呼び出さない | 現在時刻を示す赤い線の位置を描き直す |
| 予定の同期 | 「同期」ボタン押下 | `POST /api/sync/google` | ステータス欄に「同期中...」を表示し、取得した予定をカレンダーに描画して「最終同期: 時刻」に更新する。失敗時は「同期に失敗しました (status: ○○)」 |
| 表示の切り替え | 「日」「週」「月」ボタン押下 | 呼び出さない | 取得済みの予定を使って描き直す。再取得はしない |
| 日付の移動 | 「<」「>」ボタン押下 | 呼び出さない | 表示中の基準日を前後に動かして描き直す。取得範囲(今月±1ヶ月)の外には移動させない |
| 予定ダイアログを開く(新規) | 「+予定を追加」ボタン押下 | 呼び出さない | SCR-003を新規モードで開く |
| 予定ダイアログを開く(編集) | カレンダー上の予定をクリック | 呼び出さない | SCR-003を編集モードで開く |
| 予定の詳細表示 | 予定にマウスを重ねる | 呼び出さない | ポップオーバーに件名・時刻・場所を表示する。マウスが離れたら隠す |
| ToDoの追加 | ToDoフォームの送信 | `POST /api/tasks` | 成功後に`GET /api/tasks`を呼び直して一覧を更新し、入力欄を空にする |
| ToDoの完了切り替え | チェックボックスの変更 | `PATCH /api/tasks/{id}` | 完了状態を更新し、`GET /api/tasks`を呼び直して並び順を更新する |
| ToDoの削除 | 「✕」ボタン押下 | `DELETE /api/tasks/{id}` | 削除後に`GET /api/tasks`を呼び直して一覧を更新する |
| 通知をオンにする | 「🔔通知」ボタン押下(未購読時) | `GET /api/push/vapid-public-key` → `POST /api/push/subscribe` | ブラウザに通知の許可を求め、許可されたら公開鍵を取得して購読情報を登録する。ステータス欄に「通知をオンにしました(予定の10分前に届きます)」。拒否されたら「通知が許可されませんでした」 |
| 通知をオフにする | 「🔔通知」ボタン押下(購読中) | `POST /api/push/unsubscribe` | 購読情報を削除し、ステータス欄に「通知をオフにしました」 |

### SCR-003 予定追加・編集ダイアログ

| イベント | トリガー | 呼び出すAPI | 表示・処理内容 |
|---|---|---|---|
| ダイアログを開く(新規) | SCR-002の「+予定を追加」 | 呼び出さない | 入力欄を空にし、日付だけ表示中の日付を入れる。削除ボタンを隠し、ボタンを「追加」にする |
| ダイアログを開く(編集) | SCR-002の予定クリック | 呼び出さない | クリックした予定の内容を各欄に入れる。削除ボタンを表示し、ボタンを「更新」にする |
| 地図リンクの更新 | 「場所」欄の入力 | 呼び出さない | 入力内容からGoogleマップの検索URLを組み立て、リンクを表示する。未入力なら隠す |
| 予定の新規登録 | 「追加」ボタン押下 | `POST /api/events` → `PUT /api/events/{id}/category` | 入力値を検証後、Googleに予定を作成し、続けてカテゴリを保存する。成功: ダイアログを閉じ、カレンダーを描き直す。失敗: ダイアログを閉じず、エラー欄に理由を表示する |
| 予定の更新 | 「更新」ボタン押下 | `PUT /api/events/{id}` → `PUT /api/events/{id}/category` | 予定本体の更新が失敗しても、カテゴリの更新は必ず実行する。本体が失敗した場合はダイアログを閉じず、「(色の変更は反映しました)」を併記してエラーを表示する |
| 予定の削除 | 「削除」ボタン押下 | `DELETE /api/events/{id}` | 確認ダイアログで同意を得てから削除する。成功: ダイアログを閉じ、カレンダーから取り除く。失敗: エラー欄に理由を表示する |
| ダイアログを閉じる | 「キャンセル」押下、Escキー | 呼び出さない | 保存せずに閉じる。カレンダーの表示状態はそのまま保つ |

### SCR-004 Google連携完了画面

| イベント | トリガー | 呼び出すAPI | 表示・処理内容 |
|---|---|---|---|
| 画面表示 | Googleの同意画面で「許可」を押した後の自動遷移 | 呼び出さない(表示前にサーバー側でトークン交換・アカウント確認・保存が完了している) | 連携したメールアドレスを含む完了メッセージと、戻るリンクを表示する |
| ダッシュボードへ戻る | 「ダッシュボードに戻る」リンクのクリック | 呼び出さない | SCR-002へ遷移する |

## 設計判断

### 1. 操作結果の表示先を1か所に集約する

ダッシュボードで起きる操作(同期・予定の追加/更新/削除・通知の切り替え)の結果は、すべてヘッダー直下のステータス欄1か所に表示する。操作ごとに表示場所を変えると、どこを見ればよいか分からなくなるためである。

ただし、SCR-003のダイアログ内で起きたエラーだけは例外とし、ダイアログ内のエラー欄に表示する。ダイアログを開いている間は背景のステータス欄が見えないうえ、エラー時はダイアログを閉じずに入力内容を残したいためである。

### 2. 予定の取得だけ手動、天気とToDoは自動にする

画面を開いたときに自動で取得するのは天気とToDoだけとし、予定はユーザーが同期ボタンを押したときにだけ取得する。

天気とToDoは、このアプリのサーバー内(またはキャッシュの効く天気API)で完結するため、開くたびに取得しても負荷が小さい。一方で予定の取得は、Google Calendar APIへの外部通信が発生し、取得範囲も今月±1ヶ月と広い。画面を開くたびに自動で走らせると待ち時間が発生するため、必要なときにユーザーが明示的に取得する形にする。

この判断の裏返しとして、「初期表示ではカレンダーが空になる」という状態が生まれる。これは[状態のバリエーション](#状態のバリエーション-1)に明記し、仕様として扱う。

### 3. 画面の再描画は、取得済みデータの使い回しを基本とする

表示切替(日/週/月)と日付の移動では、APIを呼び直さない。1回の同期で今月±1ヶ月をまとめて取得しているため、その範囲内の移動は取得済みのデータだけで描画できる。日付ナビの移動範囲を取得済みの範囲内に制限しているのは、この方針を成立させるためである。

一方、ToDoの追加・完了・削除の後は、毎回`GET /api/tasks`を呼び直す。ToDoは「未完了を上、完了済みを下」という並び順をサーバー側のSQLで決めているため、ローカルで並べ替えを再現するより、取得し直すほうが実装が単純になるためである。件数が多くても数十件規模であり、取得コストも小さい。

### 4. SCR-004 は装飾を持たせない

Google連携完了画面にはCSSを当てない。この画面は、Google連携という管理者操作の直後に一度だけ表示され、内容(連携したアカウント)を確認して数秒で離れる画面である。見た目を整えても、それを見る機会がほとんどない。

同じく装飾の少ないSCR-001(ログイン画面)には最低限のCSSを当てている。こちらは新しい端末で開くたびに表示され、このアプリで最初に目にする画面であるという違いによる。見られる頻度と役割に応じて、かける手間を変える方針とする。

### 5. 認証はサーバー側のリダイレクトに任せる

未ログイン時の制御は、フロントエンド側では行わない。画面を開いた時点でサーバーが判定し、ログイン画面へ転送する。フロントエンド側に「ログイン済みか」という状態を持たせないことで、画面とサーバーで判定が食い違う事態を避ける。

### 6. 状態管理は画面上の変数で持つ

このアプリが保持する状態は、取得済みの予定一覧・表示モード(日/週/月)・表示中の基準日・編集中の予定IDの4つに限られる。状態管理の仕組みは導入せず、画面内の変数として持ち、変更時に描画関数を呼ぶ方式とする。

状態の数が少なく、画面も1つ(ダッシュボード)に集約されているため、仕組みを入れる利点より、構成が増える手間のほうが大きいと判断した。画面を増やす場合や、状態を複数の画面で共有する必要が出た場合は、この判断を見直す。

### 7. 外部サービスへの書き込みと、アプリ内だけの更新を分けて扱う

予定の更新時、予定本体の更新(`PUT /api/events/{id}`)が失敗しても、カテゴリの更新(`PUT /api/events/{id}/category`)は必ず実行する。前者はGoogleカレンダーへの書き込みで、自分が主催者でない予定では失敗し得る。後者はアプリ内のDBのみの更新で、必ず成功する。

[API設計](./api-db-design.md)でエンドポイントを分離した意図を、イベント設計のレベルでも維持する。これにより「件名は変更できないが、色分けだけは反映される」という挙動になり、片方の失敗がもう片方を巻き込まない。

### 8. 今回扱わない範囲

- **ローディング表示の作り込み**: 読み込み中であることはステータス欄の文言で伝え、スピナーやスケルトン表示は作らない。待ち時間が発生するのは同期とダイアログの保存のみで、いずれも数秒以内に終わるため
- **オフライン対応**: 予定の実体をアプリ側に保存しない設計のため、通信できない状態では予定を表示できない。Service Workerはプッシュ通知の受信にのみ使い、画面のキャッシュには使わない
- **セッション切れの検知**: 画面を開いたままセッションが切れた状態でAPIを呼んだ場合の挙動は、今回の設計に含めない。セッションの有効期間が1年であり、画面を開いたまま期限を迎える場面が想定しにくいためである。実装時に、APIの応答が想定と異なる場合はログイン画面へ移動する処理を入れる

## まとめ

### 設計中に苦労したこと・判断に迷ったこと

- **ToDoの更新後に一覧を取得し直すかどうか**で迷った。画面側で並べ替えを再現すれば通信は減らせるが、並び順の規則(未完了を上、完了済みを下、期限の早い順)がサーバー側のSQLにあるため、同じ規則を画面側にも書くと二重管理になる。規則を1か所に保つことを優先し、取得し直す方針にした
- **カレンダーの初期表示を空にするかどうか**も迷った。開いた瞬間に予定が見えるほうが親切ではあるが、外部APIへの通信が毎回走ることになる。同期ボタンという明示的な操作を残す方針を優先し、初期表示は空とした上で、それを「状態のバリエーション」として明記することで、仕様の抜けではないことが分かるようにした

### 学んだこと

- 状態のバリエーションを書き出す作業が、仕様の抜けを見つける手段になると分かった。「初期表示でカレンダーが空になる」「通知が非対応のブラウザではボタンを隠す」といった、正常系だけを考えていると見落とす分岐が、表に起こすことで自然に洗い出された
- イベント設計でAPIの呼び出し順序まで書くと、エラーが起きたときの挙動を設計の段階で決められると分かった。特に、予定の更新とカテゴリの更新のように、2本のAPIを続けて呼ぶ処理では、「片方が失敗したときにもう片方をどうするか」を先に決めておかないと、実装時に判断がぶれる
- 画面レイアウトと状態のバリエーションを先に決めておくと、イベント設計の「表示・処理内容」をそこへの参照として書けるようになる。レイアウト・状態・イベントは別々の成果物に見えるが、この順で作ると後工程ほど書く量が減っていく
