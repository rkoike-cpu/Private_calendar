# パーソナルカレンダー アーキテクチャ設計

[personal-calendar-concept.md](./personal-calendar-concept.md) の構想を受けての、実装アーキテクチャ設計。

## 検証結果(PoC)

`calendar-test/` にて、Go + Google Calendar APIでの動作検証済み。

- 会社のGoogle Workspace(netprotections.co.jp)で、内部向けOAuthアプリの作成・利用が可能なことを確認
- OAuth同意画面は「内部」設定で問題なし(社外公開・Google審査は不要)
- `calendar.readonly` スコープで自分の予定取得に成功
- 「内部」設定はログイン可能なアカウントを組織内に制限するだけで、アクセスする端末(スマホ含む)は問わない
- Google Calendar APIは完全無料(課金対象ではなくクォータ制。デフォルト1日100万リクエストと個人用途では枯渇しない上限)

### PoC実装上の注意点
- OAuthクライアントは「デスクトップアプリ」タイプで作成し、認可コードのやり取りは **ローカルサーバー(loopback)方式** を使用(Googleは手動コード貼り付け方式=OOBを廃止済み)
- 本番のWebアプリでは、固定ドメインの `https://` リダイレクトURIを使う **「ウェブアプリケーション」タイプ** のOAuthクライアントを別途作成する必要がある

## 全体アーキテクチャ

```
[スマホ/PCブラウザ] --HTTPS--> [Goサーバー] --GET--> Google Calendar API
                                      |--> 天気API(Open-Meteo等)
                                      |--> SQLite(トークン/キャッシュ保存)
```

### レイヤー構造の考え方
自分のアプリのAPI(ブラウザ向け)と、Google側のAPI(サーバーが呼び出す側)は別物として設計する。

- ブラウザ → 自分のGoサーバー: `POST /api/sync/google`(同期実行のトリガー。DB書き込みを伴うのでPOST)
- 自分のGoサーバー → Google: `GET .../calendar/v3/calendars/primary/events`(Google公開の読み取り専用エンドポイント)

ブラウザは直接Googleを呼ばず、必ず自分のサーバーを経由する。これにより認証トークンをブラウザ側に渡さず、サーバー側のみで安全に管理できる。

## 同期の仕様(MVP)

一定間隔の自動更新ではなく、**手動の同期ボタン方式** を採用(将来的に自動更新へ拡張可能。課金の心配はないため技術的制約はない)。

1. アプリを開く → SQLiteにキャッシュ済みの前回取得分を表示
2. 「Googleカレンダーと同期」ボタンを押す → `POST /api/sync/google`
3. サーバーがGoogle Calendar APIへGETリクエストを送り最新の予定を取得
4. キャッシュと比較し、追加・変更・削除を反映してDB更新
5. 更新後のデータをレスポンスとして返し、画面に反映

将来的に自動更新(5〜30分間隔のバックグラウンド更新)を追加する場合も、APIコール自体は無料範囲に収まるため気軽に導入可能。

## ホスティング

**Cloud Run** を推奨(Google Cloudにすでにプロジェクトがあるため親和性が高い)。

- HTTPSが自動付与される(本番用OAuthのリダイレクトURIはhttps必須のため都合が良い)
- 未使用時は0スケールでほぼ無料

## バックエンド(Go)構成要素

- **認証**: 「ウェブアプリケーション」タイプのOAuthクライアントで、固定リダイレクトURI(例: `https://<domain>/auth/google/callback`)を使用
- **セッション管理**: ログイン後にCookieセッションを発行し、**許可するメールアドレス(自分のみ)をホワイトリストでチェック**。OAuthの「内部」設定だけではアプリ自体への不正アクセスは防げないため必須
- **カレンダーモジュール**: Google Calendar API呼び出しをラップ。将来のOutlook対応を見据え、共通インターフェースを想定
- **天気モジュール**: Open-Meteo等(APIキー不要な無料サービス)を利用
- **トークン保存**: リフレッシュトークンをSQLiteに保存し、サーバー再起動のたびの再認証を不要にする
- **HTTPハンドラ**: ブラウザからのURLごとのリクエストに応答する処理(例: `/` でダッシュボードHTML、`/api/sync/google` で同期処理)

## データストレージ: SQLite

サーバー不要でファイル1つとして扱える軽量DB。個人利用の小規模アプリには十分。保存対象:

- Googleの認証トークン(リフレッシュトークン)
- 天気情報のキャッシュ
- (将来)ToDoリストなど

## ディレクトリ構成案

```
personal-calendar/
  cmd/server/main.go
  internal/
    auth/       OAuth + セッション管理
    calendar/   Google Calendar(将来Outlookも共通インターフェースで追加)
    weather/    天気API
    store/      SQLite
    handler/    HTTPハンドラ・ルーティング
  web/
    templates/  HTML(サーバーサイドレンダリング)
    static/     CSS/JS
  Dockerfile
```

フロントエンドはまずGoの `html/template` によるサーバーサイドレンダリングでシンプルに構築し、レスポンシブ対応(スマホ表示)を行う方針。SPA化は必要になった時点で検討。
