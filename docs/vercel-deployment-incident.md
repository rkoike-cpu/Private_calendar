# Vercelデプロイでの障害記録と知見

パーソナルカレンダーアプリを最初Vercelにデプロイしようとした際に発生した問題の記録。最終的にRenderへのホスティング切り替えで解決した。

## 前提: なぜVercelを選んだか

普段Vercel + Supabaseの組み合わせで開発していたため、その知見を活かせると考えて選択。Supabase(データベース)自体は最後まで問題なく、切り替えた後も継続して利用している。問題が起きたのは**Vercel上でのGoアプリのホスティング**の部分のみ。

## 発生した問題(時系列)

### 1. 環境変数の設定ミス(解決済み)
- `DATABASE_URL`をコピペする際に末尾へ改行が混入し、接続文字列のパースに失敗
- `GOOGLE_OAUTH_CREDENTIALS_JSON`も同様に、ターミナルの`cat`コマンドの出力をコピーする際、zshが付与する末尾の`%`記号(内容の一部ではなく「改行なしで終わっていますよ」という表示上の記号)を誤って含めてしまい、JSONパースに失敗

**教訓**: 環境変数の値はコード側で`strings.TrimSpace()`するなど、末尾の余分な空白・改行を許容する実装にしておくと事故が減る。

### 2. Supabaseの接続方式の問題(解決済み)
- Supabaseの「Direct connection」はIPv6アドレスを使用しており、自宅Wi-Fi(据え置き型モバイルルーター)がIPv6に対応しておらず接続不可
- 「Session pooler」(IPv4対応)に切り替えることで解決

**教訓**: Supabaseなど一部のマネージドDBは複数の接続方式を提供している。IPv6非対応のネットワークからは直接接続ではなくプーラー経由の接続を使う必要がある。

### 3. 本題: Vercel上でのリクエストパスの消失(未解決のままRenderへ移行)

Goアプリを1つのcatch-all関数(`api/index.go`)でVercelにデプロイし、内部で`net/http.ServeMux`によるルーティングを行う構成を取った。ここで以下の現象が発生:

- `vercel.json`の`rewrites`で全リクエストを`/api/index`に転送する設定にしたところ、**Goの関数内で`r.URL.Path`を見ると、実際にリクエストされたパス(`/`や`/auth/google/callback`など)ではなく、常に`/api/index`になってしまう**
- ビルドログに以下の警告が出ていたが、当初は見過ごしていた:
  > `WARNING! Internal rewrites in backend framework projects now route requests using the rewritten destination path.`
- 対策として、`vercel.json`の`destination`にクエリパラメータで元のパスを埋め込み(`/api/index?path=:path*`)、Go側でそれを読んでパスを復元する実装を試みた
- 最初は正規表現記法(`(.*)`と`$1`)で書いてしまい機能しなかった。Vercelの`rewrites`はpath-to-regexp記法(`:path*`)を使う必要があった
- 記法を修正しても解決せず、さらにデバッグのため**レスポンスヘッダーに直接デバッグ情報を出力する**実装を追加したが、そのヘッダー自体が本番のレスポンスに一切現れなかった
- ビルドキャッシュを無効化して完全に再ビルドしても同じ結果だった
- コミットハッシュの一致、デプロイの成功ステータス、ドメインの紐付けなど、他の要因は全て正常であることを確認済み

**結論**: コードやデプロイ設定に明確な誤りが無いにもかかわらず、Go関数内での`http.ResponseWriter`へのヘッダー設定が本番レスポンスに反映されないという、通常のバグでは説明しにくい挙動が観測された。Vercelの Go サーバーレス関数ランタイム(Node.js/Next.js向けほど成熟していない可能性がある)と、「1つの関数が内部で独自ルーティングを行う」という構成の組み合わせに、何らかの相性問題があったと推測している。

## デバッグ手法についての知見

- **Vercelダッシュボードのログ検索は信頼性が低い**: 同じ条件で検索しても「ログが見つかりません」と出たり出なかったりする現象が繰り返し発生した。存在するはずのログが表示されないことがあるため、「ログに出てこない=実行されていない」と即断しないほうがよい
- **`vercel logs`コマンドはライブ監視ではなく1回きりのスナップショット取得**: 実行した瞬間までの直近ログを取って終了する。`curl`と同時実行するのではなく、`curl`を先に実行してから`vercel logs`を実行する順序にする必要がある
- **`curl -v`でレスポンスヘッダーを直接確認する方法が、ログを頼るより確実だった**: ブラウザの表示やダッシュボードのログよりも、生のHTTPレスポンスを直接見るほうが速く確実に状況を切り分けられた

## 最終的な対応: Renderへの切り替え

VercelのGoサーバーレス関数をやめ、**Render**(普通の常駐サーバーとしてGoバイナリを実行するホスティングサービス)に切り替えたところ、追加のコード変更なし(`api/index.go`と`vercel.json`を削除しただけ)で問題なく動作した。

**教訓**: `net/http`で独自のルーティング・ミドルウェアを組んだGoアプリを動かす場合、Vercelのような「リクエストごとに関数を呼ぶサーバーレス変換」を挟むプラットフォームより、Render/Fly.io/Railway/Cloud Runのような「Goバイナリをそのまま常駐プロセスとして実行する」プラットフォームのほうが、余計な変換層による不具合のリスクが低い。Vercelは元々Next.js/Node.js向けに最適化されたプラットフォームであり、他言語のサーバーレス対応は制約が多い可能性がある。

## 今後、同様の状況で試すべきこと(次回への申し送り)

1. Goアプリを独自ルーティングごとサーバーレス化するのではなく、最初から「常駐サーバー型」のホスティング(Render等)を優先的に検討する
2. 環境変数は必ずコピー&ペーストで扱い、手入力・手動転記を避ける。コード側でも`TrimSpace`等の防御的な処理を入れる
3. 本番動作確認は、ブラウザの表示だけでなく`curl -v`で直接HTTPレスポンスを確認する習慣をつける
4. デプロイ先のログ機能を過信せず、必要なら独自のレスポンスヘッダーや稼働確認用エンドポイントを用意して直接検証する
